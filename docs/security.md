# Choir Collective — Security & Authorization Architecture

## Security Philosophy

Choir Collective enforces defense-in-depth across 3 mandatory boundaries:

```
[ UI / Client ] ──(No Security Trust)──> [ Server Action / API ] ──(RBAC Check)──> [ PostgreSQL RLS ]
```

1. **Client UI (Level 1):** Hides buttons and links based on user role. Not treated as a security boundary.
2. **Server Actions & API Handlers (Level 2):** Enforces server-side user authentication (`requireUser()`), RBAC permission verification (`requirePermission()`), and input validation.
3. **Database Row Level Security (Level 3):** PostgreSQL RLS policies evaluate `auth.uid()` and `auth.role()` on every database query, ensuring users cannot bypass API controls.

## Authentication & Session Lifetime

- **Session Persistence:** Session cookies generated by Supabase SSR are configured with `maxAge: 31536000` (1 year) in `src/proxy.ts`. Users remain logged in until explicitly clicking **Log Out**.
- **JWT Claim Propagation:** When a user's role is updated in `profiles`, a PostgreSQL trigger (`sync_role_to_metadata`) updates `auth.users.app_metadata.role`, providing zero-latency JWT role verification without extra DB lookups in middleware.

## Audit Logging (`src/lib/audit.ts`)

Sensitive administrative operations record immutable log records in `public.audit_logs`:
- Direct user creation
- Role changes
- Member join request approvals/rejections
- Profile updates and deletions
- Song modifications
